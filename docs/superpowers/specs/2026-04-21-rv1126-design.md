# RV1126 机器人面馆视觉交互系统 — 设计方案

## 1. 项目概述

### 1.1 场景描述
机器人面馆有三种餐品（面条/米粉/馄饨）。餐台下方有空碗，上方有 5 位转盘，顾客将碗放在碗托上触发机器人制餐，等待出餐。

### 1.2 目标
在 RV1126 嵌入式设备上实现一套视觉识别 + 语音引导 + 远程视频 + 配置管理的完整前端系统，与已有后台服务器对接。

### 1.3 约束条件
- 硬件：瑞芯微 RV1126（双核 Cortex-A7 + NPU 2.0 TOPS）
- 编程语言：Python
- 视觉加速：NPU + YOLO + OpenCV
- 语音：edge-tts（Microsoft Edge TTS，可离线缓存）
- LLM 备用：通义千问（阿里云 DashScope）
- 编程注释与交互语言：中文

## 2. 系统架构

### 2.1 总体架构（轻量级单体）

RV1126 端运行单一 Python 主进程，内部按模块组织：

```
┌─────────────────────────────────────────────────────────────────┐
│                        后台服务器（已有）                          │
└──────────────────────┬──────────────────────────────────────────┘
                       │ HTTP
┌──────────────────────▼──────────────────────────────────────────┐
│                      RV1126 端（本方案）                           │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                 持续检测驱动主循环                          │   │
│  │  客户检测 → 语音引导     碗位检测 → 自动录像（有碗录/无碗停）   │   │
│  └─────────────────────────────────────────────────────────┘   │
│         ▲                      ▲                               │
│         │                      │                               │
│  ┌──────┴───┐ ┌────┴────┐ ┌───┴───┐ ┌─────┴────┐ ┌───┴────┐  │
│  │ 视觉模块  │ │ 语音模块 │ │通信模块│ │ 视频流模块 │ │Web 服务 │  │
│  │(YOLO+OPCV)│ │(edge-tts)│ │(HTTP) │ │(RTSP+录制) │ │(Flask)  │  │
│  └──────────┘ └─────────┘ └───────┘ └──────────┘ └────────┘  │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │              LLM 备用模块（通义千问 API）                   │   │
│  │     本地检测置信度低时，上传图片/音频获取云端识别结果          │   │
│  └─────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────┘
```

选择轻量级单体架构的原因：开发周期短、模块间通信简单（直接函数调用）、部署方便、RV1126 资源有限。代码组织上预留模块化接口，后续可平滑演进为多进程架构。

### 2.2 核心模块职责

| 模块 | 职责 | 关键技术 | 文件路径 |
|------|------|----------|----------|
| **视觉模块** | 检测客户靠近（由远及近）、检测碗位状态变化、ROI 区域推理 | YOLOv5 (RKNN NPU 加速 / OpenCV DNN ONNX fallback) | `vision/detector.py` |
| **摄像头** | 摄像头打开、读取、自动重连 | OpenCV VideoCapture | `vision/camera.py` |
| **客户检测** | 人形框面积增长趋势判断客户由远及近 | ROI 区域内面积统计 | `vision/customer_detector.py` |
| **碗位检测** | 多帧投票 + 防抖的碗位状态检测 | 状态缓存队列 + 防抖 | `vision/bowl_detector.py` |
| **语音模块** | 播放引导语音、取餐通知 | edge-tts 合成 → ffmpeg 转 wav → aplay/afplay | `audio/tts_player.py` |
| **通信模块** | 与后台服务器收发消息、心跳 | HTTP REST (requests) | `comm/backend_client.py` |
| **视频流模块** | RTSP 推流（GStreamer appsrc）、MJPEG Web 流、本地录制 | GStreamer / ffmpeg | `video/streamer.py`, `video/recorder.py` |
| **Web 服务** | 配置页面、监控页面（MJPEG + ROI 框选）、录像管理 | Flask (render_template_string) | `web/config_server.py` |
| **LLM 备用模块** | 本地识别失败时上传图像到通义千问 | 阿里云 DashScope API | `llm/` |
| **主程序** | 初始化所有模块，持续检测驱动主循环 | 线程管理 + 异步推理 | `main.py` |

## 3. 数据流与工作逻辑

### 3.1 工作模式（持续检测驱动）

系统取消状态机，采用**持续检测驱动**模式。主循环每帧同时执行以下检测：

```
每帧处理流程：
  ├─ 读取摄像头帧
  ├─ 提交 YOLO 异步推理
  ├─ 获取最新检测结果
  ├─ 叠加检测框 / ROI / 状态文字
  ├─ 推送 RTSP 流 + 写入录像帧 + 编码 MJPEG
  ├─ 客户检测更新 → 触发则播放语音引导
  ├─ 碗位检测更新 → 状态变化上报后台
  └─ 录像控制：record_enabled=True 且有碗 → start()，否则 → stop()
```

### 3.2 检测模块行为

| 检测项 | 触发条件 | 动作 |
|--------|----------|------|
| 客户靠近 | ROI 内人形框面积增长 ≥ 阈值（默认 1.3 倍），带 5s cooldown | TTS 播报"请拿碗放在碗托上" |
| 碗放置 | 某碗位连续 N 帧 ≥ M 票确认有碗，且防抖时间已过 | 上报后台 `/device/bowl_status` |
| 碗取走 | 某碗位连续 N 帧 ≥ M 票确认无碗，且防抖时间已过 | 上报后台 `/device/bowl_status` |
| 录像启停 | `record_enabled=True` 且 `any_bowl_present=True` | 自动 start("auto") / stop() |

### 3.3 碗位检测防错检机制（关键）

由于转台会旋转，单帧检测容易误判。采用**多帧投票机制**：

1. 每个碗位维护一个状态缓存队列（最近 N 帧结果，如 N=5）
2. 每帧对每个碗位做 YOLO 检测：判断"有碗"/"无碗"
3. 只有当队列中 ≥M 帧（如 M=4/5）结果一致时，才确认状态变化
4. 状态变化后通过防抖时间（如 2 秒）避免抖动上报
5. 转台旋转期间（如有电机反馈信号），可临时暂停检测或降低灵敏度

### 3.4 视频录制与存储策略

| 条件 | 动作 | 存储方式 |
|------|------|----------|
| `record_enabled=True` 且检测到至少一个碗存在 | 开始录制，标记为"auto" | 本地循环存储 |
| `record_enabled=False` 或所有碗位均无碗 | 停止录制 | — |
| 存储超过阈值 | 自动删除最旧文件 | 按修改时间覆盖 |

存储管理：
- 使用固定大小目录（2G 可调整），超过 90% 时按修改时间删除最旧文件
- MP4 存储（ffmpeg 通过 stdin 接收主循环 BGR 帧），避免与 OpenCV VideoCapture 的 v4l2 设备冲突
- 文件名格式：`noodlecam_YYYYMMDD_HHMMSS_auto.mp4`

## 4. 与后台的接口协议

### 4.1 RV1126 → 后台（设备上报）

| 接口 | 方法 | 描述 |
|------|------|------|
| `/device/bowl_status` | POST | 碗位变化事件：bowl_id、event(placed/removed)、时间戳 |
| `/device/customer_detected` | POST | 检测到客户由远及近靠近 |
| `/device/heartbeat` | POST | 设备心跳（timestamp、status、mode）|
| `/device/video_clip` | POST | 制作过程录制片段上传（预留）|

### 4.2 后台 → RV1126（后台下发）

> 注：取消状态机后，后台不再需要通过 `/device/notify_meal_ready` 通知出餐完成来触发流程。碗状态变化和录像完全由视觉检测自主驱动。

### 4.3 Web 端 API（设备本地提供）

| 接口 | 方法 | 描述 |
|------|------|------|
| `/video_feed` | GET | MJPEG 实时视频流（multipart/x-mixed-replace）|

## 5. Web 配置与监控界面

### 5.1 访问方式

- **RV1126 本地**：浏览器访问 `http://localhost:8090`
- **局域网远程**：PC/平板访问 `http://<rv1126-ip>:8090`

### 5.2 配置页面 (`/`)

- **完整参数编辑**：涵盖 camera / vision / audio / backend / video / web / llm 全部 7 个分组
  - Camera：设备索引、分辨率、亮度、对比度、饱和度、Gamma
  - Vision：模型路径、置信度阈值、推理间隔、多帧投票 N/M、防抖时间
  - Audio：音量、语音角色、语速、音频目录、4 条播报文案
  - Backend：URL、心跳间隔
  - Video：RTSP 开关/帧率/端口/码率、录像开关/目录/最大存储
  - Web：绑定地址、端口
  - LLM：启用开关、API Key、Fallback 阈值、模型
- 需要重启生效的参数已标注提示
- **配置持久化**：保存为 `config.json`，重启后自动加载

### 5.3 监控页面 (`/monitor`)（核心功能）

- **实时视频画面**：MJPEG 流 `/video_feed`，画面上已叠加检测框（绿色=人，橙色=碗）和 ROI 区域
- **ROI 区域设定**：在视频画面上方直接拖拽框选客户检测区和碗位检测区
  - Canvas 绝对定位覆盖在 `<img>` 视频流上方，背景透明
  - 鼠标拖拽框选，所见即所得
  - 支持两种模式：客户检测区（单矩形）、碗位检测区（多矩形，带编号）
- **系统概览**：客户检测状态、碗状态（有碗/无碗，含仿真标记）、FPS、录像状态
- **检测目标表格**：实时显示检测到的目标类别、置信度、边界框坐标
- **录像开关**：一键开启/关闭录像，同步持久化到 `config.json`
- **仿真控制**："仿真碗存在"/"仿真碗不存在"/"清除仿真"按钮，强制覆盖真实检测结果用于测试

### 5.4 录像管理页面 (`/recordings`)

- 录像文件列表（文件名、大小、修改时间）
- **在线播放**：点击播放按钮直接内联观看（`<video controls>`）
- 下载按钮（带确认对话框）
- 删除按钮（带确认对话框）

## 6. LLM 备用方案（通义千问）

### 6.1 两种工作模式

| 模式 | 触发条件 | 流程 |
|------|----------|------|
| **自动 Fallback** | 本地 YOLO 置信度 < 阈值（如 0.3）或检测超时 | 截取当前帧 → 调用通义千问视觉 API → 解析返回的 JSON → 更新检测状态 |
| **手动切换** | 配置界面切换为"LLM 备用模式" | 所有视觉识别请求直接走通义千问，本地 YOLO 暂停 |

### 6.2 通义千问 API 调用

- 使用阿里云 DashScope API（多模态理解模型 qwen-vl-plus）
- 请求内容：Base64 编码的摄像头截图 + 结构化 Prompt
- 返回格式约定为 JSON，包含：客户是否靠近、各碗位是否有碗、置信度
- **降级策略**：通义 API 连续失败后自动切回本地模式

## 7. 网络摄像头与远程视频

### 7.1 三路视频输出

| 输出方式 | 技术 | 用途 | 路径 |
|----------|------|------|------|
| **MJPEG Web 流** | Flask Response (multipart/x-mixed-replace) | Web 监控页面实时预览 | `/video_feed` |
| **RTSP 推流** | GStreamer appsrc + x264enc + rtph264pay | 局域网 RTSP 客户端播放（VLC/FFplay） | `rtsp://<ip>:8554/live` |
| **本地录制** | ffmpeg stdin 接收 BGR 帧 + libx264 | 碗状态驱动自动启停，循环存储 | `recordings/noodlecam_*.mp4` |

### 7.2 视频参数

| 参数 | 配置值 | 说明 |
|------|--------|------|
| MJPEG 流帧率 | ~5 fps | Web 预览，平衡带宽和实时性 |
| RTSP 流帧率 | 15 fps | 局域网观看 |
| RTSP 编码 | H.264 (x264enc) | tune=zerolatency, 低延迟 |
| 录制分辨率 | 跟随摄像头（默认 1280x720） | 由摄像头和 config.json 决定 |
| 存储策略 | 循环覆盖，总量 ≤2G | 超过 90% 时删除最旧文件 |

### 7.3 GStreamer RTSP 实现要点

使用 `appsrc` 从主循环接收 OpenCV BGR 帧，避免与 OpenCV 同时打开 `/dev/video0` 冲突：

```
appsrc name=mysrc → videoconvert → video/x-raw,format=I420
  → x264enc tune=zerolatency bitrate=500
  → rtph264pay name=pay0 pt=96
```

## 8. 错误处理与异常恢复

### 8.1 分级错误处理

| 级别 | 场景 | 处理动作 |
|------|------|----------|
| **L1-静默恢复** | 单帧图像模糊、短暂网络抖动 | 丢弃该帧，记录日志，不中断服务 |
| **L2-降级运行** | NPU 推理失败、后台断开连接 | 切换 CPU 推理（ONNX）、本地缓存队列 |
| **L3-人工介入** | 摄像头离线、持续识别失败 | 日志报错，Web 界面显示状态 |
| **L4-安全停机** | 不可恢复错误 | 停止所有操作，保留日志 |

### 8.2 已实现的关键防护

- **摄像头断线**：OpenCV VideoCapture 自动重连（最多 3 次尝试），失败后返回空帧，主循环继续运行
- **磁盘空间监控**：录制启动前检查，超阈值时删除最旧录像
- **模型加载失败**：RKNN 加载失败时 fallback 到 OpenCV DNN；无模型时返回空检测，程序不崩溃
- **MJPEG 流断连**：服务端生成器捕获 `GeneratorExit`/`BrokenPipeError` 优雅退出；客户端 `<img onerror>` 自动重试
- **跨平台兼容**：macOS 使用 `afplay` 替代 `aplay`；非 Linux 平台跳过 v4l2 录制

## 10. 技术栈总结

| 层面 | 选型 | 备注 |
|------|------|------|
| 视觉推理 | YOLOv5 + RKNN Toolkit / OpenCV DNN | RKNN 为主，ONNX fallback 用于本机调试 |

| Web 服务 | Flask | render_template_string 内嵌模板，单文件部署 |
| HTTP 客户端 | requests | 与后台通信 |
| 工作模式 | 持续检测驱动 | 客户检测 + 碗位检测 + 自动录像，无状态机 |
| LLM API | 阿里云 DashScope SDK | 通义千问 qwen-vl-plus |
| 数据存储 | JSON 文件 (config.json) | 深合并默认配置，Web 热更新 |
| 视频流 (Web) | Flask Response (MJPEG) | multipart/x-mixed-replace |
