# RV1126 机器人面馆视觉交互系统 — 设计方案

## 1. 项目概述

### 1.1 场景描述
机器人面馆有三种餐品（面条/米粉/馄饨）。餐台下方有空碗，上方有 5 位转盘，顾客将碗放在碗托上触发机器人制餐，等待出餐。

### 1.2 目标
在 RV1126 嵌入式设备上实现一套视觉识别 + 语音引导 + 远程视频 + 配置管理的完整前端系统，与已有后台服务器对接。

### 1.3 约束条件
- 硬件：瑞芯微 RV1126（双核 Cortex-A7 + NPU 2.0 TOPS）
- 编程语言：Python
- 视觉加速：NPU + YOLO + OpenCV
- 语音：本地方案（非云端 TTS）
- LLM 备用：通义千问（阿里云 DashScope）
- 编程注释与交互语言：中文

## 2. 系统架构

### 2.1 总体架构（轻量级单体）

RV1126 端运行单一 Python 主进程，内部按模块组织：

```
┌─────────────────────────────────────────────────────────────────┐
│                        后台服务器（已有）                          │
└──────────────────────┬──────────────────────────────────────────┘
                       │ HTTP/WebSocket
┌──────────────────────▼──────────────────────────────────────────┐
│                      RV1126 端（本方案）                           │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                    业务状态机 (State Machine)              │   │
│  │  空闲 -> 检测到客户 -> 引导拿碗 -> 检测到放碗 -> 制作中 -> 取餐  │   │
│  └─────────────────────────────────────────────────────────┘   │
│         ▲           ▲           ▲           ▲           ▲      │
│         │           │           │           │           │      │
│  ┌──────┴───┐ ┌────┴────┐ ┌───┴───┐ ┌─────┴────┐ ┌───┴────┐  │
│  │ 视觉模块  │ │ 语音模块 │ │通信模块│ │ 视频流模块 │ │配置服务 │  │
│  │(YOLO+OPCV)│ │(本地TTS) │ │(HTTP) │ │(RTSP+录制) │ │(Web/本地)│  │
│  └──────────┘ └─────────┘ └───────┘ └──────────┘ └────────┘  │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │              LLM 备用模块（通义千问 API）                   │   │
│  │     本地检测置信度低时，上传图片/音频获取云端识别结果          │   │
│  └─────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────┘
```

选择轻量级单体架构的原因：开发周期短、模块间通信简单（直接函数调用）、部署方便、RV1126 资源有限。代码组织上预留模块化接口，后续可平滑演进为多进程架构。

### 2.2 核心模块职责

| 模块 | 职责 | 关键技术 |
|------|------|----------|
| **视觉模块** | 检测客户靠近（由远及近）、检测碗位状态变化、ROI 区域推理 | YOLOv5/v8 (RKNN NPU 加速)、OpenCV |
| **语音模块** | 播放引导语音（"请拿碗放在碗托上"）、取餐通知 | pyttsx3 / Piper TTS / 预录制音频 |
| **通信模块** | 与后台服务器收发消息（碗位变化、订单状态、设备心跳） | HTTP REST / WebSocket |
| **视频流模块** | RTSP 推流（可配置 1帧/s）、本地循环录制（≤2G）、远程播放 | FFmpeg / GStreamer、RTSP 服务器 |
| **配置服务** | ROI 区域设定保存、碗位标定、参数管理、本地/LLM 模式切换 | Flask/FastAPI 本地 Web 服务 |
| **LLM 备用模块** | 本地识别失败时上传图像/文本到通义千问，返回识别结果 | 阿里云 DashScope API |
| **业务状态机** | 协调各模块，管理从检测到取餐的完整流程 | Python 状态机 |

## 3. 数据流与状态机

### 3.1 顾客点单全流程

```
[空闲] --(视觉检测到客户由远及近)--> [引导中]
   ↑                                   │
   │                                   ▼
[完成] ◄--(客户取走碗/超时复位)-- [制作中] ◄--(后台通知出餐完成)
   │                                   ▲
   │         (若碗被取走，上报后台)      │
   └──[等待取餐] ◄--(语音播报"请取餐")--┘
```

各状态触发动作：
- **空闲**：视觉模块持续检测客户 ROI 区域，语音静默，视频流按配置推流
- **引导中**：语音播报"请拿碗放在碗托上"，高亮空碗位，视频开始标记录制"点单片段"
- **制作中**：视觉模块持续检测各碗位（多帧投票防错检），状态同步后台，视频持续录制"制作片段"
- **等待取餐**：语音播报"您的餐已准备好，请取餐"，视觉检测碗被取走则上报后台，回到空闲
- **完成/超时**：若长时间未取餐，上报后台，通知服务人员协助取餐。

### 3.2 碗位检测防错检机制（关键）

由于转台会旋转，单帧检测容易误判。采用**多帧投票机制**：

1. 每个碗位维护一个状态缓存队列（最近 N 帧结果，如 N=5）
2. 每帧对每个碗位做 YOLO 或opencv检测：判断"有碗"/"无碗"
3. 只有当队列中 ≥M 帧（如 M=4/5）结果一致时，才确认状态变化
4. 状态变化后通过防抖时间（如 2 秒）避免抖动上报
5. 转台旋转期间（如有电机反馈信号），可临时暂停检测或降低灵敏度

### 3.3 视频录制与存储策略

| 场景 | 动作 | 存储方式 |
|------|------|----------|
| 检测到客户靠近 | 开始录制，标记为"点单片段" | 本地循环存储 |
| 放碗确认 | 继续录制，合并为"制作片段" | 本地循环存储 |
| 出餐完成 | 结束录制，上传后台（或后台拉取） | 本地保留 1周或设定时间后覆盖 |
| 常规时段 | 按配置 1帧/s 推流 RTSP，可选是否本地存 | 循环存储，总量 ≤2G |

存储管理：
- 使用固定大小目录（2G可调整），超过时按时间 oldest 删除
- MP4 分段存储（每段 1-5 分钟），便于检索和上传
- 文件名含时间戳和事件类型，如 `20260421_143022_order_001.mp4`

## 4. 与后台的接口协议

### 4.1 RV1126 → 后台（设备上报）

| 接口 | 方法 | 描述 |
|------|------|------|
| `/device/bowl_status` | POST | 碗位变化事件：哪个碗位、新放/取走、时间戳 |
| `/device/customer_detected` | POST | 检测到客户由远及近靠近 |
| `/device/heartbeat` | POST | 设备心跳（在线状态、温度、错误码、模式） |
| `/device/video_clip` | POST | 制作过程录制片段上传，或提供下载 URL |

### 4.2 后台 → RV1126（后台下发）

| 接口 | 方法 | 描述 |
|------|------|------|
| `/device/notify_meal_ready` | POST | 煮面机器人通知出餐完成 → 触发语音取餐 |
| `/device/update_config` | POST | 后台远程更新设备配置（ROI、参数等） |
| `/device/control` | POST | 后台远程控制（重启、切换本地/LLM 模式、停止/启动） |

## 5. ROI 与碗位配置界面

### 5.1 支持两种操作方式

1. **RV1126 本地接显示器/触摸屏**：直接通过浏览器访问 `http://localhost:8080`
2. **局域网内远程配置**：PC/平板访问 `http://<rv1126-ip>:8080`

### 5.2 配置界面功能

- **摄像头实时预览**：显示当前摄像头画面
- **ROI 绘制工具**：鼠标/触摸框选客户检测区、5 个碗位检测区
- **碗位标定向导**：转盘静止时拍摄多张照片，标记各碗位基准状态（有碗/无碗）
- **参数微调**：YOLO 置信度阈值、多帧投票 N/M 值、防抖时间、语音音量等
- **模式切换**：本地模式 / LLM 备用模式 / 纯 LLM 模式
- **配置持久化**：保存为本地 JSON/YAML 文件，重启后自动加载

## 6. LLM 备用方案（通义千问）

### 6.1 两种工作模式

| 模式 | 触发条件 | 流程 |
|------|----------|------|
| **自动 Fallback** | 本地 YOLO 置信度 < 阈值（如 0.5）或检测超时 | 截取当前帧 → 调用通义千问视觉 API → 解析返回的 JSON → 更新状态机 |
| **手动切换** | 配置界面或后台指令切换为"纯 LLM 模式" | 所有视觉识别请求直接走通义千问，本地 YOLO 暂停 |

### 6.2 通义千问 API 调用

- 使用阿里云 DashScope API（多模态理解模型，如 qwen-vl）
- 请求内容：Base64 编码的摄像头截图 + 结构化 Prompt（描述任务、ROI 坐标、期望返回格式）
- 返回格式约定为 JSON，包含：客户是否靠近、各碗位是否有碗、置信度
- **降级策略**：通义 API 连续 3 次失败后，自动切回本地模式，30 分钟后重试

## 7. 网络摄像头与远程视频

### 7.1 混合方案（用户选定）

- **实时监控**：RTSP 推流（FFmpeg/GStreamer），远程通过 VLC/浏览器播放，延迟 1-3 秒，支持多客户端并发
- **本地存储**：MP4 分段录制，循环存储 ≤2G
- **按需上传**：出餐完成后，自动上传对应时段的视频片段到后台服务器或云存储

### 7.2 视频参数

| 参数 | 配置值 | 说明 |
|------|--------|------|
| 实时流帧率 | 1 帧/s（可配置） | 降低带宽和存储压力 |
| 录制分辨率 | 720p 或 1080p | 根据摄像头和带宽调整 |
| 编码格式 | H.264 | 兼容性最佳 |
| 存储策略 | 循环覆盖，总量 2G | 超过时删除最旧文件 |

## 8. 错误处理与异常恢复

### 8.1 分级错误处理

| 级别 | 场景 | 处理动作 |
|------|------|----------|
| **L1-静默恢复** | 单帧图像模糊、短暂网络抖动 | 丢弃该帧，记录日志，不中断服务 |
| **L2-降级运行** | NPU 推理失败、TTS 引擎异常、后台断开连接 | 切换备用方案（CPU 推理、预录音频、本地缓存队列） |
| **L3-人工介入** | 摄像头离线、磁盘满、持续识别失败 | 播放故障提示音，LED/界面显示错误码，上报后台告警 |
| **L4-安全停机** | 温度过高、硬件故障、不可恢复错误 | 停止所有电机控制，保留日志，等待重启 |

### 8.2 关键边界防护

- **磁盘空间监控**：每 15 分钟检查，低于 500MB 时自动清理最旧录像；低于 200MB 时停止录制并告警
- **内存泄漏防护**：各模块输出内存占用日志，主进程监控，RSS 超过阈值时建议整机重启
- **摄像头断线**：OpenCV VideoCapture 自动重连（3 次尝试），失败则进入 L3 告警
- **网络断连**：本地缓存事件队列（内存 + 临时 SQLite），网络恢复后批量上报

## 9. 测试策略

### 9.1 测试分层

| 层级 | 内容 | 方式 |
|------|------|------|
| **单元测试** | 状态机转换、ROI 坐标计算、多帧投票算法、磁盘清理策略 | pytest，在开发机上运行 |
| **集成测试** | 模块间协作：视觉→状态机→语音、通信模块→后台 Mock | pytest + 本地 Mock 后台 |
| **硬件在环测试** | 真实 RV1126 + 摄像头，验证 NPU 推理性能、RTSP 推流稳定性 | 实机测试，需现场布置 |
| **端到端测试** | 模拟完整顾客流程：人靠近→放碗→模拟后台出餐通知→取碗 | 人工或脚本配合实机 |

### 9.2 关键测试场景

- **碗位检测**：转台旋转时，碗位 A→B→C 变化过程中不应触发错检
- **多客户端并发**：RTSP 流同时被 3-5 个客户端播放，验证稳定性
- **网络抖动**：后台连接断连 1-5 分钟，验证事件队列缓存与重传
- **磁盘满边界**：模拟 2G 存储写满，验证循环覆盖 oldest 文件
- **LLM 备用切换**：本地 YOLO 置信度设为极低，验证通义 API 调用与结果回传

### 9.3 性能基线（RV1126）

| 指标 | 目标 | 验证方式 |
|------|------|----------|
| YOLO 推理帧率 | ≥10 FPS（NPU 加速） | 实机连续运行 1 小时统计 |
| 端到端延迟（检测到放碗→上报后台） | ≤2 秒 | 集成测试打点 |
| RTSP 推流延迟 | ≤3 秒 | VLC/FFplay 播放测试 |
| 整机内存占用 | ≤400MB | `free` 监控 |
| 启动时间（上电到进入空闲状态） | ≤30 秒 | 实机计时 |

## 10. 技术栈总结

| 层面 | 选型 | 备注 |
|------|------|------|
| 视觉推理 | YOLOv5/v8 + RKNN Toolkit | NPU 加速，RKNN 模型预转换 |
| 图像处理 | OpenCV-Python | 摄像头采集、ROI 裁剪、预处理 |
| 语音合成 | pyttsx3 / Piper / 预录音频 | 纯离线方案，无需网络 |
| 视频流/录制 | FFmpeg / GStreamer | RTSP 推流 + MP4 分段录制 |
| 配置 Web 服务 | Flask 或 FastAPI | 轻量，内嵌设备 |
| HTTP 客户端 | requests / httpx | 与后台通信 |
| 状态机 | transitions 库或手写 | Pythonic，易测试 |
| LLM API | 阿里云 DashScope SDK | 通义千问多模态理解 |
| 数据存储 | SQLite（事件缓存）+ 文件系统（配置、录像） | 无需额外数据库服务 |
